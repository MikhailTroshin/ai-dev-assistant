## 1. Поддержка нескольких репозиториев одного продукта

Сейчас система жёстко привязана к одному репо через `ML_REPO_PATH`
(один `working_dir` для всех задач). Цель — объединить репозитории продукта.

**Конфигурация проектов** — заменить единственный `ML_REPO_PATH` на реестр:

```python
# config/settings.py
PROJECTS: dict[str, ProjectConfig] = {
    "ragllm":    {"path": "/home/ws/mtroshin/ragllm",     "default": True},
    "frontend":  {"path": "/home/ws/mtroshin/fe",          "default": False},
    "infra":     {"path": "/home/ws/mtroshin/ai_assistant","default": False},
}
```

**Что сделать:**
- Кнопка/команда выбора активного проекта (FSM: «проект» становится частью контекста задачи).
- В схеме БД `tasks` добавить колонку `project` (миграция), сохранять при постановке задачи.
- В `worker.py` / `claude_runner.py` подставлять `working_dir` выбранного проекта.
- В промпт подмешивать карту смежных репо («этот сервис вызывает X из репо `frontend`»),
  чтобы Claude понимал кросс-репо зависимости.

**Кросс-репо операции:** `/rebase`, `/code-review` должны уметь работать одновременно
с несколькими репо (например, ревью MR в `frontend` по задаче, затрагивающей API в `ragllm`).

## 2. «Карта взаимосвязей» проектов (вместо NotebookLM)

NotebookLM — закрытый облачный продукт, загружать туда внутренний код небезопасно
(утечка исходников). Лучше построить **локальную карту зависимостей**, которая
обновляется автоматически.

- **Индексатор** (фон, по cron / на git-hook): обходит все репо, собирает:
  - gRPC/proto-контракты между сервисами (`ragllm/grpc/` ↔ клиенты);
  - импорты общих пакетов;
  - ссылки в docs/MR/коммитах между репо;
  - API-эндпоинты и их потребителей.
- **Хранение** — граф в SQLite/Neo4j или JSON-файл + векторный индекс
  (переиспользовать то, что уже умеет `ragllm`: BM25/BERT/DSI).
- **Использование** — при `/task` или `/ask` ассистент сам подтягивает «соседей»
  затронутых файлов и показывает: «эта правка в `retriever` влияет на
  `frontend/search-widget.tsx`».

Эффект NotebookLM (карта связей + ответы по корпусу), но внутри периметра.

## 3. Хранение документации

Варианты по возрастанию сложности:
- **Markdown в git** (`docs/` в каждом репо + общий `docs-product/`) — просто,
  версионирование бесплатно. **Рекомендуется как база.**
- **Obsidian/vault** поверх тех же `.md` — если нужен граф ссылок глазами человека.
- **qmd** имеет смысл **только если** уже есть Qt Quarto-пайплайн/отчёты; как
  первичное хранилище doc избыточен. Подходит для генерации отчётов по задачам
  (code-review, rebase-логи).

Решение: `.md` в git как единый источник правды + автогенерация артефактов
(в т.ч. `.qmd`/PDF для тяжёлых отчётов) из результатов задач.

## 4. Авто-ретрив нужной информации для задач

Сейчас промпт для Claude — плоская строка. Добавить слой контекста.

**Перед запуском Claude** worker собирает релевантный контекст:
1. По Jira-ключу — описание, вложения, комментарии;
2. По файлам из MR/diff — их текущее содержимое + соседние модули;
3. Из карты взаимосвязей (п.2) — затронутые сервисы;
4. Из doc-индекса (п.3) — релевантные `.md`.

**Реализация:** переиспользовать retriever из `ragllm` (BM25+BERT) или поднять
локальный эмбеддинг-индекс по всем репо. Ранжировать чанки, класть топ-N в
системный промпт с указанием источников. В таблице `tasks` сохранять
`context_sources` (какие файлы/документы подтянулись) — для прозрачности и отладки.

**Минимальный первый шаг:** расширить `claude_runner` так, чтобы перед задачей он
вызывал функцию-ретривер и вставлял результат в `--append-system-prompt`. Авто-ретрив
без переделки архитектуры.
